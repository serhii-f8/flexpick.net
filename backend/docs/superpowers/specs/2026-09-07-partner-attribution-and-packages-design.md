# Partner Attribution Cookie, Partner Navigation, and Report Packages

Status: Approved (design), ready for implementation planning
Date: 2026-09-07
Builds on: `2026-08-30-partner-reselling-cash-payments-design.md` (the
"base spec"). Where this document contradicts the base spec, this document
wins; each such point is marked **Amends base §N**.

## 1. Goal

Six changes to the partner-reselling feature on the `partner-reselling`
branch:

1. One unobtrusive referral parameter (`rc`) backed by a long-lived,
   tamper-proof cookie for anonymous visitors and by the database for
   registered users, so a referred customer keeps seeing their partner's
   prices across URL changes, browser restarts, and logouts.
2. The Referrals menu is visible only to Partner-plan tenants.
3. A separate, production-safe seeder for the nine report packages.
4. Partner-plan tenants cannot reach the change-plan section.
5. Every cash order from a partner's referred customers appears in the
   partner's Orders section, notifies the partner, and is approved by the
   partner with the same workflow admins have.
6. A Pricing Settings section where partners manage their selling prices
   relative to platform prices.

## 2. Findings that shaped the design

- The link a partner currently shares (`?referralCode=REF-…`) comes from the
  boilerplate's personal Referrals feature (`ReferralCode`, `Referral`,
  `ReferralService`), not from the partner system. `PartnerReferralLink`
  exists as a table but nothing creates rows or shows a link, and its
  `?partnerCode=` parameter is reachable only from tests.
- No seeded plan carries `enables_reseller_program`, so no tenant can pass
  `PartnerCapabilityService::tenantIsActivePartner()` outside tests.
- `StripeProvider::findOrCreateStripeSubscriptionProductPrices()` reuses a
  stored provider price ID whenever one exists, regardless of the local
  `PlanPrice`. Changing the price of an existing plan slug would therefore
  keep charging the old amount at Stripe. New packages must use new slugs.
- The pricing page renders every visible monthly plan as one card in one
  grid (`components/plans/all.blade.php`). Nine cards need grouping.

## 3. Referral parameter and attribution persistence

### 3.1 One parameter: `rc`

`ReferralConstants::HTTP_PARAM_REFERRAL_CODE` becomes `'rc'`. The value is
the user's existing personal code (`REF-` + 12 characters, generated by
`ReferralService::getOrCreateReferralCode()`). `ReferralService::getReferralLink()`
emits `?rc=…`. The `referralCode` and `partnerCode` query parameters are no
longer recognized anywhere. `PartnerConstants::HTTP_PARAM_PARTNER_CODE`,
`TrackPartnerReferralCode`, `SessionConstants::PARTNER_REFERRAL_CODE`, the
`PartnerReferralLink` model, factory, migration-created table (dropped by a
new migration), and their tests are removed. **Amends base §4.2.**

### 3.2 Resolving a code to a partner tenant

`PartnerAttributionService::resolveTenantForCode(string $code): ?Tenant`
now resolves through the personal code: `ReferralCode::where('code')` →
its `user` → that user's tenants (`User::tenants()`) filtered by
`PartnerCapabilityService::tenantIsActivePartner()`. If exactly one tenant
qualifies it is the partner; if several qualify the lowest `id` wins (a
deterministic rule, documented in code; multi-partner membership is not a
supported configuration); if none qualify the code is not a partner code
and yields `null`. Personal referral tracking (`Referral` rows) continues to
work for non-partner codes exactly as before.

### 3.3 The attribution cookie

A new cookie, name from `config('partner.cookie_name')` (default `fp_rc`),
holds the raw code string. It is written through Laravel's cookie queue so
the `web` group's `EncryptCookies` middleware encrypts and MACs it; a
client cannot forge or alter it, only delete it. Attributes: lifetime
`config('partner.cookie_lifetime_days')` (default 365), `httpOnly`,
`secure` when the request is HTTPS, `SameSite=Lax`.

`TrackReferralCode` middleware (already in the `web` group) is extended:

1. If `rc` is present and is a string of at most 64 characters, store it in
   session under `SessionConstants::REFERRAL_CODE` (this drives the
   personal `Referral` row at registration, unchanged).
2. If, additionally, the code resolves to a partner tenant (§3.2) **and**
   the request carries no valid attribution cookie yet, queue the cookie.
   **First touch wins**: an existing cookie is never overwritten by a
   different code, and no "already attributed" notice is shown.
   **Amends base §4.3 (conflict handling).**
3. If the visitor is authenticated, step 2 is skipped entirely: a signed-in
   user's attribution is the database and nothing else.

The session-based partner code is gone. `PartnerAttributionService`
replaces `rememberPendingCode()` / `pendingCode()` / `clearPendingCode()`
with `cookieCode(Request|null): ?string` (reads and validates the cookie)
and `queueCookieFor(Tenant $tenant, User $user)`; the pending-code
consumers (`attribute()`, `PartnerPricingResolver::tenantFromPendingCode()`)
read the cookie instead.

### 3.4 Database is the source of truth after registration

`users.partner_tenant_id` stays set-once and immutable (base §4.3).
`attribute()` runs at registration (`UserService::createUser`) and at
login (`AttributePartnerOnLogin`), reading the cookie code; the source enum
values `REGISTRATION` and `LOGIN` are unchanged.

After both events, whether or not attribution changed, the cookie is
**refreshed from the database**: if `users.partner_tenant_id` is set, the
cookie is rewritten with a code that resolves to that tenant (the partner
tenant's first member holding a personal `ReferralCode`, created on demand
via `getOrCreateReferralCode()`), with a fresh one-year lifetime. If the
user has no partner, the cookie is left untouched. A logged-out browser
therefore keeps showing the partner's prices, and a stale or different
cookie can never outvote the database for a signed-in user.

Attribution sources `LINK` and `ORDER` remain declared and undispatched, as
today.

### 3.5 Pricing resolution

`PartnerPricingResolver::computePartnerTenant()` is unchanged in shape:
authenticated → `users.partner_tenant_id` only; anonymous → cookie code
resolved through §3.2. All four "usable offering" gates and the Offline
preconditions stay as they are.

### 3.6 Personal referral rewards for partner codes

When `ReferralService::trackReferral()` is called with a code that resolves
to a partner tenant (§3.2), the `Referral` row is still created (so the
partner's My Referrals table lists the referred user and the stats widget
counts them) but reward processing is skipped: `processReward()` returns
early for a referral whose code resolves to a partner tenant, and the
`Referral` stays at `verified`/`paid` without ever reaching `rewarded`.
Partners are paid through their margin, not through coupons. Non-partner
referrals keep the existing reward behaviour. **Consistent with base §4.4.**

### 3.7 What remains visible to a determined visitor

An anonymous visitor who deletes the cookie sees base prices until they
next follow a partner link, sign in, or register. This is accepted: without
an account there is nothing server-side to bind to. Everything else the
request asked for holds: a registered user's prices are fixed by the
database, an anonymous visitor's by a cookie they cannot edit or replace
with a different partner's code.

## 4. Partner navigation group

A new Filament navigation group `Partner` (registered in
`DashboardPanelProvider::navigationGroups()` after `Billing`) contains, in
this order: **Referrals**, **Orders**, **Pricing Settings**. The old
`Referrals` group is removed.

Every item in the group is gated by a new shared helper,
`PartnerCapabilityService::userCanAccessPartnerArea(?Tenant, ?User): bool`,
which is true only when the current tenant is an active partner. Each
resource additionally applies its own `TenancyPermissionConstants`
permission as today:

| Item | Resource | Permission |
| --- | --- | --- |
| Referrals | `ReferralResource` (existing, re-grouped) | none beyond membership |
| Orders | `PartnerOrderResource` (renamed from `PartnerOrderApprovalResource`) | `PERMISSION_MANAGE_PARTNER_ORDERS` |
| Pricing Settings | `PartnerPricingSettings` page (new, §7) | `PERMISSION_MANAGE_RESELLER_CATALOG` |

`ReferralResource::canAccess()` becomes `referral enabled AND active
partner`. `ReferralRewardResource::canAccess()` becomes `false` for partner
tenants and keeps its current rule otherwise; since the group it lived in
is gone it moves under `Billing`. `ReferralLinkWidget::canView()` follows
`ReferralResource::canAccess()`. The widget's copy changes from "earn
rewards" to "Customers who sign up through this link buy at your prices."

## 5. Change-plan section for partner tenants

`SubscriptionService::canChangeSubscriptionPlan()` gains a final condition:
the subscription's tenant is **not** an active partner
(`PartnerCapabilityService::tenantIsActivePartner($subscription->tenant)`).
This single rule hides the Change Plan action on the subscriptions table,
the view page, and the `PlanUsageWidget` link, all of which already call it.

Two server-side guards are added so a typed URL is denied too:
`ChangeSubscriptionPlan::mount()` aborts 403 when the rule is false for the
routed subscription, and `SubscriptionController::changePlan()` redirects
back with an error under the same rule. The admin panel's change-plan action
is untouched: an admin may still move a partner between plans.

## 6. Report packages seeder

### 6.1 Configuration

`config/pricing.php` gains a `packages` block, the single source of truth
for the nine packages (A15 rule: no seeder or export may hold a literal
figure of its own). Each entry:

```php
'audit-diagnostic-5' => [
    'tier' => 'diagnostic',            // AuditTier value; which credit key it grants
    'name' => 'Diagnostic Report × 5',
    'actions' => 5,
    'unit_price' => 4900,               // FlexPick unit price, cents
    'price' => 23275,                   // FlexPick package price, cents
    'discount_percent' => 5,
    'partner_unit_price' => 10000,      // suggested partner selling price per report
    'description' => 'CTOs, product owners, and business leaders who want to evaluate team efficiency and basic code health.',
],
```

The full table, prices in cents:

| Slug | Actions | Package price | Suggested partner package price |
| --- | ---: | ---: | ---: |
| `audit-diagnostic-5` | 5 | 23275 | 47500 |
| `audit-diagnostic-15` | 15 | 66150 | 135000 |
| `audit-diagnostic-30` | 30 | 117600 | 240000 |
| `audit-deep-ai-5` | 5 | 56525 | 118750 |
| `audit-deep-ai-15` | 15 | 160650 | 337500 |
| `audit-deep-ai-30` | 30 | 285600 | 600000 |
| `audit-expert-5` | 5 | 474525 | 807500 |
| `audit-expert-15` | 15 | 1348650 | 2295000 |
| `audit-expert-30` | 30 | 2397600 | 4080000 |

Tier display names: Diagnostic Report, Deep AI Code Review, Expert Audit.
A test asserts `price == round(unit_price * actions * (1 - discount/100))`
for every entry so the config cannot drift from the table.

The existing `subscriptions` block (Starter, Growth, Agency, Enterprise) is
emptied and its four plan slugs (`audit-starter-monthly` etc.) move to
`retired.plans`. `app:export-pricing` exports `packages` in place of
`subscriptions`; the marketing site's consumer of that file is out of scope
here and is noted as follow-up.

### 6.2 `ReportPackagesSeeder`

A new `Database\Seeders\ReportPackagesSeeder`, registered in
`DatabaseSeeder` after `AuditMonetizationSeeder`, and runnable alone in
production with `php artisan db:seed --class=ReportPackagesSeeder`. It is
idempotent on slug:

- One `Product` per package (`updateOrCreate` on `slug`): name,
  description (the best-use-case text), features (three lines: "N
  <tier> reports per month", "Full detailed reports", "PDF export"),
  `metadata` = the three `audit_*_credits` keys with the package's
  `actions` on its own tier's key and `0` on the others, plus
  `partner_suggested_price` (the package selling price in cents) and
  `package_actions`; `is_default = false`; `reseller_quota_keys = []`
  (partners resell fixed packages; no quota overrides).
- One `Plan` per product (`updateOrCreate` on `slug` = product slug +
  `-monthly`): monthly interval, `interval_count 1`, `FLAT_RATE`, no
  trial, active, visible.
- One `PlanPrice` per plan (`updateOrCreate` on `currency_id`) at the
  package price.
- Retirement: plans listed in `pricing.retired.plans` are set
  `is_active = false, is_visible = false` and their products
  `is_popular = false`. Nothing is deleted; no subscription, order, price
  row, or provider-price mapping is touched.

Because every package is a **new** slug, the Stripe stale-price problem
(§2) cannot arise. A re-run after a local price edit updates `plan_prices`
only; the seeder never touches `plan_price_payment_provider_data`, and a
test documents that an existing provider mapping survives a re-run.

The seeder also stamps `enables_reseller_program => true` into the
existing `audit-partner` product's metadata (merging, not replacing, its
credit keys). That hidden, $0, admin-assigned plan is the Partner plan.
**Amends base §3**, which asked for a distinct paid plan; there is no paid
partner offer today, and the flag is metadata, so a paid plan can be added
later by seeding another product with the same flag.

### 6.3 Pricing page grouping

`components/plans/all.blade.php` groups the monthly cards by
`product.metadata.audit_tier_group` — a new metadata key the seeder writes
(`diagnostic` / `deep_ai` / `expert`) — into three sections headed with
the tier display name and its one-line description from
`pricing.tiers`. Plans without the key (the demo/testing seeders, any
manually created plan) render in one trailing unlabelled grid exactly as
today, so nothing outside the packages changes shape. The same component
serves the dashboard change-plan page, which therefore inherits the
grouping.

## 7. Pricing Settings page

A new Filament page `App\Filament\Dashboard\Pages\PartnerPricingSettings`
(slug `pricing-settings`, group `Partner`, icon `heroicon-o-tag`) replaces
`PartnerPlanCatalogResource` and `PartnerProductCatalogResource`, which are
deleted along with their pages and tests (their coverage moves to the new
page's test). The page hosts two tables via Filament's `InteractsWithTable`:

**Plans** — every visible, active plan (`Plan::where('is_visible', true)`
with `is_active`), columns: Package, Platform price, Your price, Margin
(your price − platform price, or "—" when unconfigured), Status
(`Enabled` / `Disabled` / `Below minimum`). **One-time products** — same
columns over visible active `OneTimeProduct`s.

Row action **Set price** opens a form with one money input (dollars, not
cents; converted on save) and a **Resell** toggle. The input's default is,
in order: the existing offering's price; else
`product.metadata.partner_suggested_price`; else the platform price. The
form's helper text shows the platform price as the floor. Saving calls
`PartnerCatalogService::setPlanOffering()` / `setProductOffering()` with an
empty `quota_overrides` array; validation and error display stay as today.
No quota inputs are rendered (all seeded `reseller_quota_keys` are empty;
the service still validates whatever it receives).

Access: `canAccess()` = `userCanAccessPartnerArea()` AND
`PERMISSION_MANAGE_RESELLER_CATALOG`.

## 8. Partner Orders

### 8.1 Scope of the list

`PartnerOrderResource` (slug `partner-orders`, label **Orders**, group
`Partner`, `$isScopedToTenant = false`) lists every `Order` whose buyer is
attributed to the current tenant:

```
orders.partner_tenant_id = :tenant
OR EXISTS (users u WHERE u.id = orders.user_id AND u.partner_tenant_id = :tenant)
```

Tabs: **Pending** (default; `status = PENDING AND is_local`), **All**,
**Approved** (status `SUCCESS`), **Rejected** (`REJECTED`). Columns:
Customer, Type (purchase / renewal), Item (plan or product name), Payment
(Cash / provider name), Base price, Your price, Margin, Status, Created.
Base price and margin show "—" for gateway orders, which the partner did
not price.

The customer-facing `OrderResource` in the same panel is unchanged.

### 8.2 Cash orders from referred customers belong to the partner

`PurchaseSnapshotService::forPlan()` / `forProduct()` set
`partner_tenant_id` to the buyer's `users.partner_tenant_id` whenever the
buyer is attributed to an active partner, **even when no usable offering
exists**; `base_price_snapshot` and `quota_snapshot` are computed as today
(base metadata when there is no offering). `OrderService` /
`SubscriptionService` continue to merge the snapshot unconditionally, so a
gateway order by a referred customer also carries `partner_tenant_id`; that
is what §8.1's first predicate reads, and it is informational only.

Consequences, replacing the approver column of base §8.2's table:

| Item for an attributed customer | Shown at | Checkout | Approver |
| --- | --- | --- | --- |
| Configured, enabled offering | partner price | Offline only | partner |
| Not configured / disabled | base price | any provider | partner if Offline was chosen; n/a for a gateway |

**Amends base §8.2 (approver) and §7.3**: an admin remains able to approve
or reject any pending cash order as a support override, but is no longer
the *expected* approver for a referred customer's base-priced cash order.
`OrderApprovalService::assertPartnerMayAct()` is unchanged: it already
checks `order.partner_tenant_id`, which is now set for these orders.

### 8.3 Notifications

`NotifyPartnerOfPendingCashOrder` (email, on `OrderedOffline`) is unchanged
and now fires for every referred customer's cash order because of §8.2.

In addition, the dashboard panel enables Filament database notifications
(`->databaseNotifications()` on `DashboardPanelProvider`, plus the standard
`notifications` table migration). The same listener sends a
`PartnerNewOrderNotification` (Laravel `Notification`, `database` channel)
to each recipient it emails, with the customer, item, amount due, and an
action linking to the Orders page's Pending tab. Recipients are the tenant
members holding `PERMISSION_MANAGE_PARTNER_ORDERS`, as today.

### 8.4 Approve and reject

Row actions Approve and Reject are visible only on rows where
`OrderApprovalService::isPendingCashOrder()` is true and
`order.partner_tenant_id` equals the current tenant; they call
`approveAsPartner()` / `rejectAsPartner()` with the optional note, exactly
as the current resource does. The view action opens a read-only infolist
mirroring the admin's order view minus the approval-history section.

## 9. Configuration summary

New `config/partner.php`:

```php
return [
    'cookie_name' => env('PARTNER_COOKIE_NAME', 'fp_rc'),
    'cookie_lifetime_days' => (int) env('PARTNER_COOKIE_LIFETIME_DAYS', 365),
];
```

`config/pricing.php`: `packages` added; `subscriptions` emptied;
`retired.plans` extended.

## 10. Data model changes

- Drop table `partner_referral_links`.
- Add table `notifications` (Laravel standard).
- No column changes. `products.metadata` gains keys
  `partner_suggested_price`, `package_actions`, `audit_tier_group` on the
  nine packages and `enables_reseller_program` on `audit-partner`.

## 11. Removed code

`PartnerReferralLink` model, factory, `PartnerReferralLinkTest`;
`TrackPartnerReferralCode` middleware and test; `PartnerConstants`;
`SessionConstants::PARTNER_REFERRAL_CODE`; `PartnerPlanCatalogResource`,
`PartnerProductCatalogResource`, their pages and tests. The base spec's
`partner_referral_links` entry in §12 is superseded.

## 12. Testing strategy

PHPUnit feature tests, following the existing partner test files:

- **Middleware**: `rc` sets the session code; sets the cookie only for a
  partner code and only when absent; never overwrites; ignores non-string
  and over-long values; skips the cookie for an authenticated user;
  `referralCode` and `partnerCode` are ignored.
- **Attribution**: registration and login attribute from the cookie;
  cookie refreshed from the database after both, including when the cookie
  held a different partner's code; a user with no partner keeps their
  cookie untouched; set-once still holds.
- **Resolution**: personal code → partner tenant; non-partner code → null;
  lapsed partner plan → null; multi-tenant deterministic choice.
- **Rewards**: partner referral creates a `Referral` row but never a
  coupon; a non-partner referral still earns one.
- **Pricing resolver**: anonymous cookie drives partner prices; a logged-in
  direct customer with a stale cookie sees base prices.
- **Navigation**: the Partner group and each item appear only for an
  active partner tenant with the right permission; `ReferralRewardResource`
  hidden for partners. Extend `DashboardMenuItemsTest`.
- **Change plan**: action hidden and page/controller denied for a partner
  tenant; unchanged for a direct customer.
- **Seeder**: nine products/plans/prices with the exact cents; metadata
  credit keys and suggested prices; idempotent on re-run; a manual price
  edit on a package is reset by a re-run while a provider price mapping
  survives; old plans retired with subscriptions intact; `audit-partner`
  gains the flag and keeps its credits; the arithmetic check in §6.1.
- **Pricing page**: three tier sections; ungrouped fallback for plans
  without the key.
- **Pricing Settings**: access gating; default price order (offering,
  suggested, platform); save path and floor violation message; product
  table.
- **Partner orders**: list includes base-priced cash orders and gateway
  orders of referred customers, excludes other tenants' orders; tabs;
  approve/reject only on own pending cash orders; snapshot stamps
  `partner_tenant_id` without an offering; email and database notification
  both sent per recipient.

Pint, `pint --test`, and Larastan must stay clean, per CI.
