One live key: GIF search fallback

Valid, low
backend/libs/capabilities/src/gif-search.service.ts:12
Finding
A testing-tier key for the third-party GIF search API is hardcoded as a fallback when the deployment does not configure its own key.
Impact
The key is limited to 100 requests per minute and grants access to public GIF search only. Anyone can use it and exhaust its quota, which would throttle GIF search. It grants no access to Skaile data or systems.
Action
Remove the fallback so GIF search requires a configured key, and revoke the testing key with the provider.

Deep file review

Swarm mode runs agents without the egress firewall

Confirmed
backend/libs/session/src/broker/swarm-container-manager.ts:66
Assessment
Correct. When a session's firewall plan is anything other than open, the swarm driver logs a warning and starts the container unrestricted. The session lifecycle already refuses to start a session whose plan cannot be resolved, and this driver already refuses to start when required mounts are missing, so this is an inconsistency with our own fail-closed intent.
Exposure
The swarm driver is used only by the agents-executor service, which is deployed to staging. Production agents run on the Docker driver, which enforces the firewall.
Action
Make the swarm driver refuse to start when it cannot enforce a non-open plan. This is a release blocker for swarm mode in production.

Unknown providerType falls through to the GitHub adapter

False positive
backend/libs/credential/src/provider-connection.service.ts:234
Assessment
The fallthrough exists in the service, but it cannot be reached. The only caller is the provider-connections tRPC route, which validates providerType against a closed enum of six values. All six have adapters, and the registry registers them unconditionally. A caller cannot submit an unregistered type.
Action
None required. We may replace the fallthrough with an explicit error as a hardening change.

Connector-flag compare-and-swap excludes providerLinkId

By design
backend/libs/session/src/skaile-config.service.ts:201
Assessment
The exclusion is intentional and documented at the site, so that background provider-link reconciliation does not fail user flag edits. The flags involved (exposeAccessToken, watch) require at least User role on the session to change. A link can only be bound to a connector if the session owner is authorised to use it, and a database guard enforces that on every bind. A concurrent repoint therefore cannot expose a credential to anyone who is not already entitled to it.
Action
None.

Session slug retry does not converge across API replicas

Latent
backend/libs/session/src/session-creation.service.ts:160
Assessment
Accurate, and already documented in the code. Production runs a single API process, so the retry always converges today.
Action
Revisit before the API is scaled horizontally.

Typing-indicator visibility filtered in the browser

Already mitigated
backend/libs/router-trpc/src/routes/workspace.route.ts:2263
Assessment
The server removes recipientUserIds before broadcasting typing state, so clients never receive the recipient list. The most another participant can learn is that someone is typing a private message. Verifying this surfaced a small functional bug: intended recipients also do not see the indicator for private messages, because the client filter relies on the list that the server removes. We will fix that, and update a stale code comment that still describes the older behaviour.
Action
UX fix only. No security change needed.

No dependency lockfile

False positive
Assessment
The project uses Bun, and bun.lock is committed at the repository root and in frontend/ and other packages. Bun's current lockfile is a text file named bun.lock, not the older binary bun.lockb. The scanner probably only recognises the older name.

No runtime error monitoring

Partly valid
Assessment
Production logs are collected centrally and are queryable. There is no dedicated exception-tracking or alerting service. We treat this as a product decision rather than a defect.

Corrections to the repository facts

  • CI configured: "no". The repository has 17 GitHub Actions workflows under .github/workflows/, and the report's own summary says CI is present.
  • Potential secrets: "0". This contradicts the 131 credential findings reported elsewhere in the same document.
  • Test file ratio: "0%". This contradicts the 1,919 test files the summary cites and the testing score of 100.

The security hygiene score of 0 comes entirely from the unfiltered secret scan. With lockfile checksums and test fixtures excluded, we would expect it to change substantially on a re-run. We would welcome a re-scan once the scanner configuration below is in place.

  2. Remove the hardcoded GIF-search fallback key and revoke it with the provider.The only live key found.
  3. Add a .gitleaks.toml that allowlists postxl-lock.json, test files, *.example and Storybook output, and run gitleaks in CI.Removes the noise so that a real leak would stand out.
  4. Remove the committed Storybook build output.Structure finding.
